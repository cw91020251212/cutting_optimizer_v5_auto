# 鋁材切割最佳化工具：手機 UI/UX 專業審查與設計交接

**文件狀態：** 僅供設計決策與後續實作交接。本文不授權任何外觀修改，亦不包含 CSS、HTML 或程式碼變更。  
**審查基礎：** 目前公開介面的 390 × 844 手機畫面。[1] [2]

## 結論

三位獨立 reviewer 的結論一致：現時介面的主要問題不是個別按鈕的樣式，而是**版面沒有以現場使用者的任務流程作骨架**。第一屏把大型標題、七個未標示工具與混合設定放在最前面，真正高頻的「輸入切割件」卻被擠到畫面下方。加上不同漸層、高光、陰影、色彩和圓角同時出現，使用者難以判斷甚麼是目前任務、甚麼是主要操作、甚麼只是輔助功能。

後續視覺重設應採用「**精密鋁材工作站**」的方向。這個方向以可量測、耐用、冷靜和快速操作為主，不把頁面設計成海報，也不以多個彩色元件堆砌存在感。設計必須先固定工作流程、資訊層級與元件責任，然後才處理顏色、字級、間距與動效。

> **不可直接在現有卡片上壓縮、搬位或覆蓋 CSS。** 必須先定義新資訊架構與 wireframe，再按核准規格實作。

## 審查範圍與限制

本審查基於一張 390 × 844 的手機截圖。畫面下方的材料輸入、計算按鈕及結果區沒有完整出現，因此對那些區段提出的是**結構建議**，不是對既有功能的事實斷言。任何設計落地前，都必須在實機驗證數字鍵盤、iOS 與 Android 安全區、繁中／英文長文字、字體放大、錯誤狀態與至少 44 × 44 px 的觸控目標。

## 三位 reviewer 的共同發現

| 範疇 | 發現 | 設計含意 |
|---|---|---|
| 首屏優先次序 | 大型產品標題、七個圓形工具和 Settings 卡佔據大部分可見高度。核心的切割件輸入只露出開頭。 | 首屏必須先讓使用者開始輸入切割需求。頁首只保留名稱和一個工具入口。 |
| 工作流程 | 「設定、切割件、材料、結果」以卡片序號並列，但沒有建立完成狀態、資料摘要或下一步。 | 以「切割需求 → 原料庫存 → 計算 → 結果」作為主流程。 |
| 設定分層 | 結果單位、演算法、鋸縫、方案管理與自動補料放進同一張卡，但它們使用頻率和時機不同。 | 依任務時機拆開：鋸縫靠近材料；演算法收進進階設定；方案與顯示偏好移到工具入口。 |
| 輸入效率 | 長度被拆成 m／cm／mm 三個欄位，每筆資料需多次定位與輸入。 | 優先採單一長度數值欄位加單位選擇，或提供可解析的「1.2m」「1200mm」輸入。若因資料模型必須保留三欄，必須以一個群組容器和清楚規則呈現。 |
| 主次操作 | Save、Load 與 Auto Replenish 在設定卡中比輸入資料更突出。 | 每個工作區只保留一個主要行動。儲存、載入、匯出與說明屬次要動作。 |
| 工具可理解性 | A+、A-、主題、調校、說明、Ex、QR 都是未標示圓形按鈕。 | 低頻工具應移到「更多／工具」選單。保留的每個控制必須有可見文字或明確標籤。 |
| 視覺語言 | 多重漸層、高光、厚重陰影、布紋背景與青／綠／黃／紫同時競爭。 | 建立單一設計 token 系統。色彩應傳遞狀態與層級，而不是純裝飾。 |
| 人體工學與回饋 | 高頻輸入被低頻頂部控制擠壓；底部常駐狀態列可能遮擋內容。 | 高頻輸入與主要 CTA 應在中下屏。狀態訊息應就近顯示或短暫 toast，不能覆蓋表單。 |

## 建議的資訊架構

### 頁面殼層

頁首應縮為單行應用列。左側顯示「鋁材切割最佳化」，右側只保留一個明確命名的「更多／工具」入口。字體調整、主題、說明、範例、QR、匯出和系統資訊均應放在此入口，避免佔用主工作區。

頁首下方使用可辨識的四段式工作進度：**切割需求、原料庫存、計算、結果**。每一步必須有文字，並以完成、目前、錯誤或未開始狀態回饋；不能只以 `1/4` 或顏色徽章傳達進度。

### 步驟一：切割需求

這是預設展開、首屏優先的區域。每一筆切割件應讓使用者快速輸入長度與數量；用途屬可選欄位。區塊內應有明確的資料摘要，例如「切割件：8 筆，共 12,400 mm」，以及唯一的主要行動「新增切割件」。新增、編輯、刪除和欄位錯誤必須在該區就近呈現。

### 步驟二：原料庫存

原料區應以和切割需求相同的資料列邏輯呈現，包括原料長度、可用支數與必要的材料屬性。鋸縫厚度是本次計算的材料／工藝參數，應在此區預先填入推薦值。自動補料亦應視為材料策略；只有開啟後才顯示補料長度與規則。

### 進階最佳化設定

演算法、餘料處理優先序、容差等內容屬低頻設定。預設應收合為「進階最佳化設定」，並以一句清楚的推薦策略作摘要。這樣可保留原有求解器功能，同時避免首次使用者必須先理解技術名詞。

### 方案與顯示偏好

結果顯示單位、字體、主題、儲存、載入、重新命名、刪除與匯出均屬偏好或管理工作。它們不應阻擋一次新計算的開始。載入方案可以在流程開始前由工具入口進入；儲存方案應在資料有效或計算完成後作為次要操作出現。

### 計算與結果

當至少有一筆有效切割需求和一筆有效原料時，應顯示唯一的主要 CTA：「計算最佳切法」。在 CTA 附近顯示資料完整度與缺漏原因。計算完成後，結果首先提供摘要，包括所需原料支數、利用率、總餘料、無法排入項目；其後才展開每支原料的切割計畫、鋸縫和餘料細節。

## 視覺系統方向

### 色彩與材質

介面應以**深石墨／冷灰**作為框架，以低對比的霧面淺灰或暖白承載表單資料。**電氣青藍**只用於主要操作、聚焦及導引；**安全黃**只用於步驟進度或提醒；**綠色**只代表成功或已儲存；**紅色**只代表錯誤。若紫色沒有明確產品語意，應移除。

可保留極淡、低對比的金屬質感作背景提示，但表單和資料卡必須乾淨，避免厚重高光、浮雕字、多層陰影和過量描邊。內容應以數字、欄位和狀態為焦點，而非以裝飾奪取注意力。

### 字體、尺寸與間距

應採單一易讀無襯線字體系統。標題使用半粗或粗體；表單標籤與數值使用常規或中黑；輔助文字必須保有足夠對比，不能只靠淡灰小字。數值建議採等寬字體或數字等寬特性，以強化量測與精度感。

間距以 8 px 為基準。卡片內距約 16 px，區塊間距約 16–24 px，欄位與主要按鈕高度約 48 px。卡片及控制項宜統一約 12 px 圓角；膠囊外形只保留給狀態徽章。這些規則必須整理為設計 token，不能在各區塊自行設定。

### 元件責任與狀態

每個工作區只能有一個最強主要行動。主要 CTA 使用實心青藍；次要動作使用外框或文字按鈕。圖示只能作輔助，不能取代清楚的文字名稱。警示、成功、啟用／停用不能只靠顏色，還要有文字、圖示或形狀差異。

## 落地前必須完成的 wireframe

在任何 CSS 或元件實作前，應先提交並核准以下內容：

1. 390 px 手機首屏 wireframe，清楚顯示首次進入時可看見的內容。
2. 切割需求、原料庫存、進階設定、方案管理與結果的區塊層級。
3. 空白、輸入中、資料不完整、計算中、成功與錯誤狀態。
4. 底部主要 CTA 在正常捲動、鍵盤彈出及安全區下的行為。
5. 繁中與英文下的標題、按鈕、提示與長字串換行。
6. 一套已命名的色彩、字級、間距、圓角、陰影和圖示規格。

## 實作與驗收限制

任何後續實作必須由 UI/UX reviewer 先核准 wireframe 與設計 token，然後才進行程式整合。程式整合時不得以在現有樣式末端追加大量覆蓋 CSS 的方式處理，應移除或重整舊規則後再建立清楚的元件結構。每次實作都要提供至少 390 px、375 px、430 px 三個手機寬度的截圖，並完成輸入、鍵盤、安全區、語言切換與結果流程測試。
